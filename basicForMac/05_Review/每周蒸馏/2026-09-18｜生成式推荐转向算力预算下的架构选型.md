# 2026-09-18｜生成式推荐转向算力预算下的架构选型

## 一句话蒸馏

本周的证据把问题从「生成式架构能不能替代级联管线」推进到「在交叉特征、语义 ID 质量和线上时延/QPS 预算下，应该为哪类计算付费」。知识库也完成了从 31 篇工业论文到概念卡、选题和成本报告的首次编译。

## 新增证据

- **端到端生成架构已有工业正例，但不是无边界结论。** [[OneRec：统一召回与排序的端到端生成式推荐]]、[[GenRank：大规模生成式排序的工业验证]]、[[UniROM：广告排序的端到端统一生成架构]]、[[GPR：广告推荐的统一生成式预训练范式]]、[[OneRanker：一个模型统一生成与排序]]、[[GR4AD：广告生成式推荐的架构训练推理联合设计]] 共同支持「统一生成是可落地方向」；每项仍是单篇工业论文证据，业务口径不同，证据强度为**多篇来源支持**。
- **交叉特征是生成式扩展的关键边界。** [[MTGR：保留交叉特征的工业级生成式推荐扩展]] 原文明确支持：删除交叉特征后性能大幅下降，且不能简单靠扩大参数弥补。证据强度为**原文明确支持**。
- **推理成本已从工程后置问题变成架构约束。** [[UGSep：用户侧计算复用降低大模型推理成本]]、[[OneTrans：一个Transformer统一特征交互与序列建模]]、[[GR4AD：广告生成式推荐的架构训练推理联合设计]]、[[PROMISE：过程奖励模型解锁推荐推理时扩展]]、[[MakeItLongKeepItFast：万级序列的线性复杂度建模]] 分别提供用户侧复用、KV 缓存、动态 beam、PRM 搜索和长度外推的工业证据；合成结论进入 [[生成式推荐的推理成本控制]]，证据强度为**多篇来源支持**。
- **SID 是生成质量的上游基础设施。** [[TRM：语义token取代itemID释放扩展潜力]]、[[GR4AD：广告生成式推荐的架构训练推理联合设计]]、[[MERGE：动态聚类的流式item索引范式]]、[[PROMISE：过程奖励模型解锁推荐推理时扩展]] 和 [[语义ID如何成为生成式推荐的基础设施]] 共同指向语义 token、业务感知编码、动态索引和逐步纠偏四条路线；但路线排序缺少统一基准，证据强度为**多篇来源支持**。
- **长序列收益真实，但收益函数受系统成本约束。** [[LONGER：全局token稳定超长行为序列建模]]、[[MakeItLongKeepItFast：万级序列的线性复杂度建模]]、[[LASER：分段目标注意力突破长序列延迟墙]] 和 [[超长行为序列建模的工程解法]] 显示算法与系统必须共同设计；各论文的序列长度、硬件和业务不同，证据强度为**多篇来源支持**。
- **References 回流队列出现高优先级前序工作。** [[2026-09-17｜论文引文简报：LONGER]] 与 [[2026-09-18｜论文引文简报：RankMixer]] 指向 HSTU、Wukong 和多篇推荐 Scaling Law 论文。本地只有标题、年份和关系推断，没有原文核对，证据强度为**待验证**。
- **Horizon 新闻里有少量外围推荐系统线索。** [[2026-09-16｜Horizon英文日报]] 与 [[2026-09-17｜Horizon英文日报]] 包含 LLM 品牌推荐评估、Facebook Marketplace 个性化检索多样性、Swing 检索计算和 P3Rec。它们还不是生成式推荐主线证据，证据强度为**待验证**。

## 主题提炼

### 1. 端到端替代级联管线进入「边界条件」阶段

1. **改变了什么理解**：本周证据不再支持把「替代级联」当作孤立架构胜利。OneRec、GenRank 和广告线论文说明端到端生成有工业收益；MTGR 又提醒，传统交叉特征、目标对齐和推理预算会决定这套架构能否真正胜出。核心理解从「统一生成更先进」变成「统一生成是一组配套系统的选型」。
2. **支撑材料**：[[生成式推荐为何开始替代级联管线]]、[[OneRec：统一召回与排序的端到端生成式推荐]]、[[GenRank：大规模生成式排序的工业验证]]、[[MTGR：保留交叉特征的工业级生成式推荐扩展]]、[[UniROM：广告排序的端到端统一生成架构]]、[[GR4AD：广告生成式推荐的架构训练推理联合设计]]。
3. **适用边界**：当前结论主要来自快手、小红书、美团、腾讯等工业场景和单业务 A/B。短视频、电商、广告的优化目标和曝光结构不同，不能把其中一项收入、时长或 AUC 增益迁移到所有场景。
4. **还缺什么证据**：缺少同业务下「端到端生成 + 保留交叉特征 + 传统级联」的统一对照，也缺少离线指标与长期在线留存、广告收入之间的可比较映射。

### 2. 扩展中心从参数规模迁移到算力预算

1. **改变了什么理解**：RankMixer、TokenMixer-Large、OneTrans、UGSep、GR4AD、PROMISE 和 MakeItLongKeepItFast 共同说明，scaling 不是单纯扩大模型。新增算力必须分配到参数、序列长度、beam、PRM、KV 缓存和硬件优化之间；时延/QPS 不是部署后的限制，而是架构设计的输入。
2. **支撑材料**：[[Scaling Law在工业推荐系统的落地路径]]、[[生成式推荐的推理成本控制]]、[[RankMixer：token混合让推荐模型MFU提升十倍]]、[[OneTrans：一个Transformer统一特征交互与序列建模]]、[[UGSep：用户侧计算复用降低大模型推理成本]]、[[GR4AD：广告生成式推荐的架构训练推理联合设计]]、[[PROMISE：过程奖励模型解锁推荐推理时扩展]]。
3. **适用边界**：用户侧复用适合用户表示与候选相对解耦的场景；动态 beam 和 PRM 适合错误逐步累积的生成搜索；长度外推依赖近期行为的时序局部性。各方法也不是天然可叠加，量化、缓存、beam 和 PRM 的组合需要重新实验。
4. **还缺什么证据**：缺少同一 SLO、同一业务目标和同一硬件下的成本-收益曲线。尤其是 PRM + 动态 beam、KV 缓存 + 序列压缩、用户侧复用 + 量化的叠加边界。

### 3. SID 从实现细节升级为生成质量地基

1. **改变了什么理解**：SID 不是把 item 换成离散 token 的预处理步骤，而是决定泛化、冷启动、流式更新和生成搜索上限的基础设施。TRM 关注语义 token 与记忆 token 的混合，GR4AD 关注业务目标感知，MERGE 关注非平稳分布下的动态索引，PROMISE 关注层级生成中的语义漂移。
2. **支撑材料**：[[语义ID如何成为生成式推荐的基础设施]]、[[TRM：语义token取代itemID释放扩展潜力]]、[[GR4AD：广告生成式推荐的架构训练推理联合设计]]、[[MERGE：动态聚类的流式item索引范式]]、[[PROMISE：过程奖励模型解锁推荐推理时扩展]]。
3. **适用边界**：静态语义量化适合较稳定 item 空间；业务感知 SID 适合广告、电商等强业务目标场景；动态聚类适合偏斜、非平稳流式分布，但 MERGE 当前仍部署在传统检索路径，尚未进入生成式检索。
4. **还缺什么证据**：缺少同一个下游生成任务、同一 tokenizer 质量指标和同一业务指标下的路线对比，也缺少 SID 质量与生成召回/排序质量的上界关系量化。

## 研究问题变化

- **部分回答**：「端到端生成能否替代级联」已经从可行性问题降级为边界条件问题。现有证据支持在特定工业场景替代，但还没有证明它对所有业务和流量结构通用。
- **升级**：「推理成本如何控制」应从工程分支升级为主线研究问题，因为它同时约束参数扩展、长序列、beam 搜索和测试时扩展。
- **升级**：「SID 质量如何评估」需要从技术路线描述升级为可量化问题。至少要区分索引质量、生成中间命中率、下游业务指标和冷启动表现。
- **保持开放**：「多场景负迁移何时出现」仍未被回答。各家场景定义、奖励函数和实验口径不同，尚不能给出可靠触发条件。
- **暂不归档**：「交叉特征与生成式架构如何兼得」已有 MTGR 的部分答案，但该方法主要在判别式排序扩展中验证，向纯生成式召回推广的路径仍不清楚。

## 回流建议

- **知识卡片**：建议在 [[生成式推荐为何开始替代级联管线]] 中把交叉特征、训练目标对齐和推理预算并列为替代成立的三个边界条件；在 [[Scaling Law在工业推荐系统的落地路径]] 中补充各路线的成本口径。
- **选题**：建议扩展 [[生成式推荐的推理成本控制]]，把方法分成「复用计算、降低单位计算、动态分配搜索、重设长序列训练/推理」四类，并记录每类证据的业务边界。
- **选题**：建议为 [[语义ID技术路线对比]] 建立横向证据表，字段包括索引类型、更新方式、业务信息粒度、离线评估、在线指标和当前部署范围。
- **输出**：[[语义ID技术路线对比]] 是最值得启动的下一篇输出，因为它已经有足够的多源证据，而且能反过来检验 SID 卡片的分类是否可靠。
- **归档**：本周不建议归档已有卡片。HSTU、Wukong 和 Scaling Law 前序论文应先人工核对原文，再决定是否补卡或并入现有扩展规律卡。
- **体检**：下一轮重点检查「测试时扩展律」「SID 决定生成上限」「长序列单调收益」三个表述，避免把单篇论文的收益曲线写成通用规律。
