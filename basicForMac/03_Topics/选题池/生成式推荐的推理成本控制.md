# 生成式推荐的推理成本控制

## 切入点

scaling 的收益都被时延/QPS 预算夹住，推理成本控制本身成了独立的研究方向。

## 研究问题

- 用户侧计算复用（UGSep/OneTrans KV 缓存）与量化（W8A16）的组合最优解？
- 动态 beam serving 与 PRM 引导搜索如何在预算内分配算力？
- 测试时扩展律的收益-成本曲线如何建模？

## 证据强度评估

总体强度：中。三条主要控制手段已有工业部署证据：用户侧计算复用、推理时动态搜索/验证、系统级架构优化。但它们大多来自单篇论文，缺少跨公司统一口径的成本-收益曲线。

| 结论 | 证据强度 | 判断 |
| --- | --- | --- |
| 解耦用户侧与 item 侧 token，可以复用用户侧计算并降低稠密交互模型的时延 | 原文明确支持 | [[UGSep：用户侧计算复用降低大模型推理成本]] 报告抖音 Feed 时延 -20%、AUC 仅 -0.004%，红果/千川也有时延下降；组合收益依赖模型结构。 |
| 因果序列建模配合跨请求 KV 缓存，可以显著降低长序列推理成本 | 原文明确支持 | [[OneTrans：一个Transformer统一特征交互与序列建模]] 的系统消融显示跨请求 KV cache 使训练运行时间约 -30%、推理 p99 约 -29.6%，且线上有正向收益。 |
| 轻量 PRM 引导搜索可用约 10% 推理时延换来更高中间命中率 | 原文明确支持 | [[PROMISE：过程奖励模型解锁推荐推理时扩展]] 有公开数据、工业离线和 A/B；但 10% 是其特定架构下的数字，不能泛化为 PRM 的固定成本。 |
| 动态 beam serving 能提升 QPS 并保持收入 | 原文明确支持 | [[GR4AD：广告生成式推荐的架构训练推理联合设计]] 报告 DBS 相对 GR-Base QPS +20%，最终配置有广告收入收益；未披露 A/B 流量比例和周期。 |
| 推理成本是工业 scaling 的共同约束 | 多篇来源支持 | [[Scaling Law在工业推荐系统的落地路径]] 综合多条扩展路线，均提到被时延/QPS 预算夹住。 |
| UGSep + W8A16、动态 beam + PRM、缓存 + 量化的最优组合 | 待验证 | 目前没有统一收益-成本曲线，也缺少相同 QPS/SLO/业务目标下的横向实验。 |
