# 推理成本如何约束生成式推荐扩展

## 核心观点

生成式推荐的扩展不能只问“更大模型能不能带来收益”，还要问“新增收益能不能装进线上时延、QPS 和预算”。2025-2026 年的多篇工业论文显示，推理成本已经从部署后的工程问题，变成与模型结构、训练目标和业务指标共同设计的第一约束。

目前可以说：用户侧计算复用、跨请求 KV 缓存、量化、动态 beam serving、过程奖励模型和长序列外推，都已经有工业级证据。但还不好说其中哪一种组合是通用最优解。它们依赖模型结构、item 空间、业务目标和流量曲线，缺少跨公司的统一成本-收益曲线。

## 为什么成本控制成了独立问题

传统推荐模型的扩展往往被召回、粗排、精排的级联结构切分：每个阶段只服务自己的目标，扩展压力也分散在不同链路里。生成式推荐把理解用户、生成候选、排序候选放到更统一的架构中，收益来自更完整的交互和端到端优化，但代价是推理路径也更集中。

这时单点加速往往不够。原因有三点：

1. **候选数量被放大**。一个请求里要为多个候选重复计算很多用户侧表示，用户侧重复计算会随候选规模线性增长。
2. **序列长度被放大**。长行为序列能带来收益，但注意力、存储和 I/O 的成本也随长度上升。
3. **推理路径被放大**。beam search、测试时扩展和过程奖励能提高精度，但也会把更多算力投入在线链路。

所以，扩展的关键不是“把模型做大”，而是判断新增算力应该投到哪里、哪些计算可以复用、哪些候选应该被提前剪掉。

## 第一类杠杆：复用用户侧计算

生成式推荐的请求通常具有“一个用户、多个候选”的结构。只要候选不会改变用户历史表示，用户侧计算就可以被复用。

[[OneTrans：一个Transformer统一特征交互与序列建模]] 把序列特征和非序列特征统一进一个 Transformer，并使用跨请求 KV caching。用户序列是 append-only 的，因此上一请求的 KV 可以被下一请求复用，只需要计算新增行为。系统消融显示，跨请求 KV cache 使训练运行时间约下降 30.2%，推理 p99 时延约下降 29.6%。在线 A/B 中，Feeds 场景 p99 时延下降 3.91%，Mall 场景下降 3.26%，同时业务指标仍保持正向。

[[UGSep：用户侧计算复用降低大模型推理成本]] 处理的是另一类难点：稠密 token 混合模型里，用户和候选特征在多层交互中纠缠，不能直接复用。UGSep 通过 User-Group Separation 把用户侧和 item 侧信息流显式解耦，再用信息补偿弥补掩码造成的表达损失，最后配合 W8A16 权重量化降低访存压力。在抖音 Feed 的 1:1 用户组 token 配置下，推理时延下降 20.0%，AUC 仅下降 0.004%，活跃天数、时长、点赞等在线指标没有显著差异。

这两条路线的共同规律是：先识别哪些计算与候选无关，再把它从逐候选计算中抽出来。如果用户表示和候选强耦合，就不能只靠 KV cache，而要重新设计信息流。

## 第二类杠杆：降低单位计算的访存与算子成本

当理论 FLOPs 下降后，线上时延不一定同比例下降，因为真实瓶颈可能已经从算力转到显存带宽。

UGSep 的 W8A16 就是针对这一点：权重用 8 bit 存储，激活保留 16 bit，减少权重加载压力，同时保持数值表达。OneTrans 则把 FlashAttention-2、混合精度、activation recomputation、Pyramid Stack 等系统优化组合起来。论文报告，相对未优化版本，FlashAttention 使训练运行时间下降 50.1%，混合精度加重计算使推理 p99 时延下降 69.1%。

这类方法的边界也很清楚。量化精度、kernel 支持度、batch 大小和硬件都会影响最终收益。一个方案在某一平台有效，不代表换硬件后还能保持同等收益。

## 第三类杠杆：动态分配推理算力

如果所有请求都使用同样的 beam 宽度，高峰期会被最重请求拖垮，低峰期又会浪费算力。更合理的做法是按负载、层级和候选质量动态分配。

[[GR4AD：广告生成式推荐的架构训练推理联合设计]] 的 Dynamic Beam Serving（DBS）把固定 beam 改成递增 beam，例如把 512-512-512 改成 128-256-512，并用 Traffic-Aware Adaptive Beam Search（TABS）在低峰提高 beam、高峰保持预算。论文报告 DBS 配置相对 GR-Base 的 QPS 提升 20%，同时广告收入仍有正向收益。系统里还包括短期 TTL 缓存、Beam-Shared KV Cache、TopK Pre-Cut 和 FP8。

[[PROMISE：过程奖励模型解锁推荐推理时扩展]] 提供了另一条路径：不是简单扩大 decoder beam，而是让轻量 Path-level PRM 对层级 SID 的中间路径打分，再动态剪掉错误分支。工业部署中 K+=4000 的版本只增加一个 PRM block，总参数量增加约 15%，推理时延增加约 10%，但离线召回有大幅提升，在线 A/B 也获得正向业务收益。

这两条路线说明，推理算力的最佳用法不一定是“每个候选都算得更久”，而是“把算力投入最能纠正错误的路径”。

## 第四类杠杆：重构长序列的注意力与训练方式

长行为序列是推荐系统里最确定的收益来源之一，但也是最容易撞上成本墙的地方。LONGER、MakeItLongKeepItFast 和 OneTrans 给出的不是同一个答案，而是三种工程取舍。

- [[LONGER：全局token稳定超长行为序列建模]] 用全局 token 稳定长上下文注意力，并用 Token Merge 压缩序列。它保留了较强的全局建模能力，但压缩比例会影响表达保真度。
- [[MakeItLongKeepItFast：万级序列的线性复杂度建模]] 用 STCA 把历史自注意力改成目标到历史的堆叠交叉注意力，使复杂度线性化；再用 Request Level Batching 复用同一请求内的用户编码；最后通过“短训长推”降低训练成本。
- [[OneTrans：一个Transformer统一特征交互与序列建模]] 则用因果注意力、Pyramid Stack 和跨请求 KV cache，把长序列、特征交互和缓存复用放进同一个架构。

MakeItLongKeepItFast 特别有启发性：完整 10k 训练收益约为 +0.30%，而“训练均值约 2k、推理 10k”的外推方案达到 +0.23%，相当于用约三分之一训练成本拿到约 80% 收益。这说明成本控制不只是压缩模型，也可以重新分配训练和推理阶段的算力。

## 决策框架

如果要判断一个生成式推荐系统应该优先使用哪种成本控制方法，可以先问四个问题。

| 问题 | 优先考虑的方法 |
| --- | --- |
| 用户表示是否能跨候选或跨请求复用？ | 跨请求 KV cache、用户侧计算分离 |
| 时延瓶颈是算力还是显存带宽？ | W8A16、FP8、FlashAttention、kernel 融合 |
| 精度瓶颈来自 beam 搜索的错误累积吗？ | PRM 引导搜索、动态剪枝、过程奖励 |
| 流量是否存在明显峰谷？ | 动态 beam width、低峰扩算、高峰保预算 |

但这个框架只是入口，不能代替实验。UGSep 的收益依赖 TokenMixer 结构，OneTrans 的收益依赖因果序列建模和 KV cache，PROMISE 的收益依赖层级 SID，GR4AD 的动态 beam 依赖广告生成任务的短序列多候选特点。直接迁移数字会高估收益。

## 当前证据边界

1. **缺少统一基准**。各论文使用不同业务、候选规模、序列长度、基线和 SLO，无法直接比较“1 单位推理算力”能换来多少业务收益。
2. **A/B 周期和流量比例披露不一致**。有些论文给出七天 A/B，有些给出一个月，有些没有披露流量比例。
3. **方法之间不是天然可叠加**。UGSep 加 W8A16 有明确协同，但 PRM 加动态 beam、KV cache 加更激进的序列压缩，都需要重新做系统实验。
4. **长序列的压缩损失仍难量化**。全局 token、Token Merge、Pyramid Stack 和线性交叉注意力都会改变信息保留方式，但哪类用户行为最容易被压缩掉，仍缺少统一度量。
5. **成本收益需要按业务目标定义**。广告看 eCPM 和 ROI，电商看 GMV 和订单，内容看时长和完播率。同一套方法在不同业务里的最优预算不同。

## 结论

生成式推荐的下一阶段竞争，不只是参数规模竞争，也是推理算力分配竞争。成熟的方案会把成本控制写进模型结构、训练目标和在线服务里：用户侧计算尽量复用，单位算子尽量贴近硬件，推理算力尽量投给最值得保留的候选路径。

目前最稳妥的判断是：用户侧复用和系统级优化已经能稳定降低推理成本；动态 beam 和 PRM 能在预算内提高收益上限；长序列方案则必须在精度、训练成本和线上时延之间做显式取舍。真正的问题已经从“能不能做生成式推荐”变成“在给定 SLO 下，应该为哪一类计算付费”。
