# MTGenRec：面向美团生成式推荐模型的高效分布式训练系统——动态哈希嵌入表、两阶段ID去重与动态序列批处理

## 论文信息

- **论文标题**：MTGenRec: An Efficient Distributed Training System for Generative Recommendation Models in Meituan
- **一句话结论**：MTGenRec 在 TorchRec 基础上，通过动态哈希嵌入表、自动表合并、两阶段 ID 去重和动态序列批处理，解决生成式推荐模型在工业场景中稀疏嵌入动态增删、查表通信冗余和 GPU 负载不均衡问题，训练吞吐提升 1.6×–2.4×，并在美团外卖业务取得订单量和 PV_CTR 的线上增长。
- **发现来源**：2025Meituan_MTGR
- **历史被引底稿论文数**：5

## 贡献

- 提出 MTGenRec，一个面向美团生成式推荐模型（GRM）的高效可扩展分布式训练系统。
- 针对 GRM 稀疏模型，引入动态嵌入表（哈希表）以支持特征 ID 的实时插入/删除，并设计自动表合并与两阶段 ID 去重以加速嵌入查表。
- 针对 GRM 稠密模型，提出动态序列批处理以缓解变长用户序列导致的 GPU 计算负载不均衡。
- 在美团 10 天、日均超 2 亿条用户序列的真实数据上实验，MTGenRec 相比 TorchRec 训练时间减少 2.44×，并在 100+ GPU 上展现良好扩展性。
- 系统已在美团多个应用部署，日均处理数亿请求；在外卖平台观察到用户订单量增长 1.22%、线上 PV_CTR 提升 1.31%。

## 方法要点

- 模型架构：GRM 由输入序列（上下文序列 T_con、历史序列 T_hst、曝光序列 T_exp）、嵌入层、多层 HSTU（层次化序列转换单元）和 MMoE 层组成，使用交叉熵损失训练。
- 分布式训练：沿用 TorchRec 的混合并行策略，稀疏模型用模型并行、稠密模型用数据并行，端到端同步执行；并引入流水线（copy、dispatch、compute 三流）预处理下一批数据。
- 动态嵌入表：采用键值解耦的哈希表存储布局，键结构保存 ID 到嵌入指针的映射，嵌入结构以 chunk 方式存储嵌入向量和辅助数据；使用 MurmurHash3 哈希函数和开放寻址处理冲突。
- 分组并行探测：提出分组并行探测技术，探测步长 S=(k%(M/threads-1)+1|1)*threads，保证 S 为奇数且与表大小 M=2^n 互质，从而遍历所有槽位；定理 3.1 证明奇数步长可覆盖全部 M 个槽位。
- 容量扩展：当负载因子 > 0.75 时触发扩展，键结构容量按 2 的幂次翻倍，嵌入结构维持双 chunk（当前 chunk 和下一 chunk）预分配机制，避免嵌入数据的大批量迁移。
- 自动表合并：设计统一特征配置接口 FeatureConfig（特征名、嵌入维度、查找表等）和 HashTableCollection，自动生成合并策略（如合并相同嵌入维度的表），减少查表算子数量。
- 动态表合并的 ID 偏移：由于动态表行数不可预知，无法使用固定行偏移；采用位运算将原始 ID 与特征表标识符组合成全局唯一 ID，公式为 ID=(i<<(63-k))|x，其中 k=ceil(log2(m+1))。
- 两阶段 ID 去重：第一阶段在设备内对特征 ID 去重后再进行 all-to-all ID 交换；第二阶段在 ID 交换后再次去重，避免不同设备发送相同 ID 导致的重复嵌入传输，主要降低嵌入通信延迟。
- 动态序列批处理：每个 GPU 维护序列缓冲区，以目标 token 数（平均序列长度 600 × batch size）为约束，通过累积和与二分搜索找到最佳划分点，输出前 k 条序列作为平衡批次；不足目标 token 数的样本合并到后续缓冲区。
- 梯度同步：动态序列批处理后，各设备样本数不同，采用 all-to-all 通信同步 batch size，并按 batch size 加权平均梯度，保证数值正确性。
- 其他实现技术：支持动态分布式环境下的检查点恢复（各设备独立保存，加载时通过取模定位）、混合精度训练（稠密模型 FP32→FP16，稀疏嵌入按访问频率动态划分热/冷特征）、梯度累积和算子融合。

## 实验与证据

- 数据集：美团 10 天真实用户日志，日均超 2 亿条序列，平均序列长度 600，最大长度 3000；训练集 0.21 亿用户、430 万物品、237.4 亿曝光、10.8 亿点击、1.8 亿购买；测试集 302 万用户、314 万物品、7685 万曝光、454 万点击、76.9 万购买。
- 模型设置：稠密模型按计算复杂度分为 GRM 4G 和 GRM 110G（G 为每次前向的 GFLOPs）；稀疏模型按嵌入维度因子分为 1D、8D、64D，1D 基线嵌入维度为 32–128，64D 为 1D 的 64 倍扩展。
- 环境：默认 8 GPU 训练节点，扩展实验最多 16 个节点共 128 GPU；GPU 为 NVIDIA A100 SXM4 80GB，节点内 NVLink 600 GB/s，节点间 InfiniBand 200 GB/s。
- 准确率对比：在 GRM 4G 1D 上，MTGenRec 与 TorchRec 的 CTR GAUC 和 CTCVR GAUC 训练曲线均保持正确性和稳定性（图 9）。
- 线上 A/B 测试：在美团外卖应用以 2% 流量对比持续学习 2 年的 DLRM 基线；GRM 4G 离线 CTR GAUC +0.0036、CTCVR GAUC +0.0154，线上 PV_CTR +1.04%、UV_CTCVR +0.04%；GRM 110G 离线 CTR GAUC +0.0153、CTCVR GAUC +0.0288，线上 PV_CTR +1.90%、UV_CTCVR +1.02%。
- 时间分解（100 训练步）：GRM 4G 1D 上 TorchRec 查表 7.0s、前向 14.8s、反向 50.7s，MTGenRec 查表 3.2s、前向 14.0s、反向 32.6s；GRM 110G 64D 上 TorchRec 查表 95.2s、前向 27.8s、反向 177.7s，MTGenRec 查表 14.4s、前向 19.9s、反向 54.7s。
- 消融实验：GRM 4G 1D 上，+Merging Table 吞吐 +5.3%，+ID Unique 累计 +50.0%，+Sequence Balancing 累计 +59.8%；GRM 110G 1D 上，+Merging Table +11.0%，+ID Unique 累计 +82.6%，+Sequence Balancing 累计 +144.3%；相比基线 MTGenRec 吞吐提升 1.60×–2.44×。
- 序列平衡评估：GRM 4G 1D 在 8/16/32/64 GPU 上吞吐提升 2.8%/3.9%/4.4%/6.5%；GRM 110G 1D 提升 20.0%/22.7%/29.6%/33.5%，平均提升 26.5%，64 GPU 峰值 33.5%。
- 序列平衡对 batch size 和显存的影响：GRM 4G 1D batch size 480→496，GPU 显存利用率 86.3%→95.7%（+9.4）；GRM 110G 1D batch size 80→116，显存利用率 75.3%→90.3%（+15.0）。
- 两阶段 ID 去重评估：在 4G 复杂度、1D 和 64D 嵌入维度、16 到 64 GPU 上，两阶段去重相比无去重基线吞吐提升 1.1–3.7×；Comm. unique（仅第一阶段）优于 Lookup unique（仅第二阶段）；去重收益随嵌入维度增加而增大。
- 动态嵌入表评估：与 TorchRec 的 MCH 基线对比，4G 1D 吞吐 392,731→579,649（+47.59%），4G 8D 260,590→438,190（+68.2%），4G 64D 80,857→155,832（+92.7%），110G 1D 44,719→68,993（+54.28%），110G 8D 28,329→55,929（+97.4%），110G 64D MCH 出现 OOM 而 MTGenRec 为 38,575；动态嵌入表相比 MCH 吞吐提升 1.47–2.22×。
- 扩展性评估：以 8 GPU 为基线扩展到 128 GPU，MTGenRec 在 128 GPU 达到理想加速比的 62.75%–78.5%；按计算复杂度扩展（4G 1D vs 110G 1D，27.5×）和按嵌入维度扩展（4G 2D vs 4G 64D，32×）时加速比下降较小；嵌入维度对加速比的影响比计算复杂度更显著。

## 局限与开放问题

- 论文未明确讨论动态哈希表在极端高负载或大量删除场景下的性能退化风险，仅说明负载因子 > 0.75 时触发扩展。
- 动态序列批处理采用轻量级方法，论文承认存在更复杂的负载均衡方法（如基于长度分布的序列打包或动态规划并行策略），但基于经验观察认为当前方法已接近最优，未与这些方法进行实验对比。
- 实验基线仅与 TorchRec 对比，未与其他工业训练系统（如 TensorFlow 系系统）对比，原因是这些框架目前不支持 GRM 训练。
- 线上 A/B 测试仅在外卖应用以 2% 流量进行，未报告其他业务垂类的线上效果。
- 论文未报告动态嵌入表在长时间运行下的内存碎片或哈希冲突率等细粒度指标。
- 部分实现细节（如流水线、检查点恢复、混合精度、梯度累积、算子融合）放在附录，正文未给出这些技术的独立消融实验。

## 待验证问题

- 动态哈希表在特征 ID 频繁插入和删除的生产环境中，长期运行后的内存碎片和哈希冲突率如何变化？
- 两阶段 ID 去重在不同序列长度分布和不同嵌入维度下的收益边界是什么？是否存在去重开销超过通信节省的场景？
- 动态序列批处理与更复杂的负载均衡方法（如序列打包、动态规划并行）在更大规模 GPU 集群上的效果差异如何？
- MTGenRec 的检查点恢复机制假设集群扩展遵循 2 的幂次，非 2 的幂次扩展时如何保证正确性和效率？
- 动态嵌入表的容量扩展策略（键结构翻倍、嵌入结构双 chunk）在嵌入维度极大时是否仍能保持内存效率？
- MTGenRec 在其他业务垂类（如旅行、健康）的线上效果是否与外卖一致？
- 论文中 GRM 相比 DRM 的离线 CTCVR GAUC 提升 2.88pp 与表 1 中 GRM 110G 的 +0.0288 是否一致？需要确认指标口径。

## 与知识库的关联

- 与 TorchRec 的关系：MTGenRec 基于 TorchRec 开发，沿用其混合并行策略，但针对 TorchRec 静态嵌入表无法处理动态 ID、重复 ID 通信冗余和手动表合并配置繁琐两个局限进行改进。
- 与 DRM 训练系统的关系：论文回顾了 Persia、PICASSO、XDL、ScaleFreeCTR、Zion、RecSpeed 等 DRM 训练系统，指出它们多基于 TensorFlow 且依赖特定稀疏嵌入访问模式假设，不适用于 PyTorch 的 GRM 训练。
- 与 Transformer 训练系统的关系：论文回顾了 FlashAttention、FlexFlow、GPipe、Megatron-LM、DeepSpeed、Hydraulis 等工作，指出 MTGenRec 复用注意力核优化，但 GRM 稠密模型较小，简单数据并行即可，且 MTGenRec 额外优化了 Transformer 中不存在的稀疏嵌入。
- 与生成式推荐模型的关系：MTGenRec 的 GRM 架构基于 HSTU（Actions speak louder than words: Trillion-parameter sequential transducers for generative recommendations），并引入 MMoE 预测头替代原 MLP。
- 与哈希表和开放寻址的关系：动态嵌入表使用 MurmurHash3 和开放寻址，并针对高负载因子下的聚集问题提出分组并行探测，引用线性探测相关研究（Bender et al., FOCS 2022）。
